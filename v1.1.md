# V1.1 Overlay Evidence And Replay Plan

Working note from the 2026-05-22 Dallara P217 LMP2 / Gesamtstrecke Long capture and diagnostics deep-dive.

This file is intentionally evidence-oriented. It records what the current bundles prove, what they do not prove, and the V1.1 tool shape that would make this analysis repeatable instead of forensic.

## Collection Boundary

V1.1 high-fidelity evidence must stay opt-in.

On Windows, the app should only start raw capture and any V1.1 per-frame model/pixel replay sidecars after the user intentionally enables **Enhanced iRacing Telemetry Capture** in Support before joining/driving. The existing `TelemetryCapture:RawCaptureEnabled=true` configuration path can remain a developer/test-build escape hatch, but diagnostics should report that as the opt-in source. It should not look like silent default collection.

When enhanced capture is off, ordinary diagnostics can still collect bounded counters, route activity, compact overlay diagnostics, performance summaries, and final/last-active snapshots. They should not collect raw `telemetry.bin`, live per-frame overlay payloads, or live pixel/screenshot evidence as V1.1 artifacts.

The offline `overlay_forensics.py` path is different: it can analyze a `capture-*` directory that was already supplied. That is post-processing of an explicit capture, not a new background collection mechanism.

Storage rule:

- Raw session truth and live high-fidelity sidecars belong under the explicit `%LOCALAPPDATA%\TmrOverlay\captures\capture-*` folder that enhanced capture created.
- Diagnostics bundles under `%LOCALAPPDATA%\TmrOverlay\diagnostics` may include compact summaries, manifests, evidence-quality warnings, and references to the latest capture, but they should not become the primary store for raw telemetry or bulky V1.1 replay artifacts.
- App-owned forensics packages belong under `%LOCALAPPDATA%\TmrOverlay\forensics\<capture-id>`. Enhanced capture finalization creates the starter package automatically. The offline tool can enrich that package from the explicit `capture-*` input, while `--output artifacts/overlay-forensics/<capture-id>` remains useful for disposable dev-workspace experiments.

## Evidence Quality

The raw captures are the best source for what the telemetry said. The diagnostics bundles are mostly finalization snapshots plus counters.

Important limitation: both full-race diagnostics were created from `session_finalization` after the iRacing session ended. Current and last-active overlay model snapshots often say hidden, disconnected, stale, or telemetry unavailable. Those final states are not direct proof of what was rendered during the live race.

Live performance was captured, but the bundle summary hides most of the timeline:

- `metadata/performance.json` is a final aggregate snapshot.
- `performance/performance-20260522.jsonl` has continuous samples, roughly every 30 seconds.
- In race 2, performance samples run through the capture window and show capture progress reaching `206109` frames with pending message count `0`.

Pixel evidence is missing:

- `metadata/evidence-quality.json` warns `live_overlay_screenshot_capture_disabled`.
- It also warns `visible_overlays_without_pixel_evidence` and `visible_overlays_without_current_screenshots`.
- That means we can prove route/API behavior and raw model inputs, but not exact OBS pixels for each overlay.

V1.1 should treat this as a first-class product gap. Every live capture should preserve enough sampled live model and pixel evidence to answer: "what did each surface render, and did it match the raw telemetry at that moment?"

### Garage Cover

Garage Cover did not fail to load in OBS. OBS loaded `/overlays/garage-cover` and polled it heavily:

- Race 1: `/api/overlay-model/garage-cover=26333`, `garage-cover|model-hidden=1398`, `garage-cover|model-render=0`
- Race 2: `/api/overlay-model/garage-cover=46348`, `garage-cover|model-hidden=2458`, `garage-cover|model-render=0`

The image and route were ready in both diagnostics:

- `routeEnabled=true`
- `routeStatus=listening`
- `imageStatus=ready`
- `imageFileName=cover.png`
- `imageLength=5380858`

The model stayed hidden because the product layer reported `disabled | product hidden`.

Policy clarified after the Navarra OBS retest:

- OBS route polling proves only that the browser source is connected.
- The live cover should render only when Garage Cover is enabled in TMR settings and fresh telemetry reports `IsGarageVisible=true`.
- Disconnected, waiting, stale, settings-preview, and garage-hidden states should not cover.

Important caveat: the sampled raw captures show `IsGarageVisible=false` for all sampled frames in both full races. That means these two raw captures do not prove a live garage-screen transition occurred. They do prove that the OBS source was product-hidden the entire time even though the route and image were ready.

Fix direction:

- Expose the Garage Cover visibility toggle in settings so the product-enabled state is explicit.
- Keep the settings Preview region image-only; it must not force the live OBS cover open.
- Add deterministic replay fixtures with enabled/disabled, `IsGarageVisible=true`, garage hidden, stale telemetry, disconnected telemetry, and image missing/ready states.

### Flags

Flags have the strongest local-context evidence gap. The race-long meatball in these captures was real, so duration alone must not classify a meatball as false.

Race 1 raw diagnostics:

- `framesWithDisplayFlags=105014` out of `122998`.
- `displayKindCounts.Meatball=90905`.
- Longest display was `Critical:Meatball` for `515.199` seconds.
- `0x10140000 -> Critical:Meatball:Repair` happened on `68091` frames.

Race 2 raw diagnostics:

- `framesWithDisplayFlags=49375` out of `206109`.
- `displayKindCounts.White=28325`.
- `displayKindCounts.Checkered=13906`.
- `displayKindCounts.Black=862`.
- Longest display was `Finish:White` for `281.345` seconds.

Likely risk area:

- `src/TmrOverlay.App/Overlays/Flags/FlagsOverlayViewModel.cs` maps global `SessionFlags` bits directly to driver-visible critical flags.
- `RepairFlag=0x00100000` becomes `FlagDisplayKind.Meatball`.
- `FurledFlag=0x00080000` contributes to black/furled display.
- In these captures, the race 1 meatball must be preserved as real/local-driver-supported or manually annotated real. Other long-lived global-derived critical/finish states still need local/session-context validation before the overlay treats them as driver-visible state.

OBS caveat:

- OBS never loaded Flags in either full-race bundle: `html=0`, `model=0`, `render=0`.
- So this is a raw/native/model correctness issue, not an observed OBS pixel issue from these bundles.

Fix direction:

- Revisit whether global `SessionFlags` can ever drive local-driver critical flags without driver-specific validation.
- Prefer car-index-specific flag sources for local black/meatball state if available.
- Add raw capture replay assertions for the two full races so confirmed real meatball state is retained, while black/white/checkered/furled states require local-driver or session-state evidence.

The main takeaway is that the new capture plumbing is useful enough to separate several problem classes, but it still does not save the active live overlay truth we need to fix every issue from one package.

What we learned:

- App-owned forensics under `%LOCALAPPDATA%\TmrOverlay\forensics\<capture-id>` is the right user experience, but the auto-created package is currently a bootstrap/index package. - OBS was open during the v1.1.0 test: diagnostics saw OBS 32.1.2 and an `obs-browser-page` process. The localhost logs still showed only `stream-chat` route traffic, so "OBS not working" is now an OBS source/readiness classification problem, not simply "OBS was closed" or "localhost was down."

### Fuel Calculator Compact Height

Symptom:

- Fuel Calculator did not shrink when only two rows were visible.

Current code-path read:

- Shared sizing already has a compact path: `OverlayContentSizing.FuelCalculatorHeightForContent(rowCount, sectionCount)` clamps row/section geometry between the minimum compact height and the full default height.
- Native/browser recommended sizing uses `OverlayContentSizing.FuelCalculatorHeight(...)`, which derives expected rows from enabled Fuel Calculator blocks for the current session.
- Browser/localhost model evidence has a second pass in `BrowserOverlayModelFactory.FuelBrowserSourceHeight(...)` that derives height from the rendered `MetricSections` row/section count when `model.ShouldRender=true`.
- That leaves several likely failure modes: the live model rendered two rows but the native form or OBS source stayed at the persisted/default size; enabled content blocks implied more rows than the live sections actually displayed; scale/custom dimensions locked the surface; or the browser CSS content height changed while the source/canvas size did not.

Forensics fields needed:

- Session kind, enabled Fuel Calculator content blocks, `model.metricSections` titles/row counts, `effectiveSettings.rendered.browserSource.baseHeight/height/scale`, `effectiveSettings.rendered.layout.unusedHeightRatio`, CSS `--fuel-content-height`, OBS source/client rect if available, Windows native form/client size, and an explicit size reason such as `settings-content`, `rendered-content`, `custom-size`, or `persisted-window`.

## Screenshot And Replay Test Tiers

Screenshot manifest parity should be treated as a product contract test. Its job is not only to catch pixel drift; it should prove that browser review, localhost/OBS, and Windows native render the same production behavior from the same data and settings.

Tier 1: CI contract fixtures.

- Small, committed, deterministic fixtures run on every PR.
- Each overlay should have populated, unavailable/no-data, chrome-on/no-data where applicable, chrome-off where applicable, session-mode, content-toggle, minimum-scale, OBS-route, and alias/source scenarios.

- Commit tiny frame/model summaries extracted from real V1.1 captures, not full `capture-*` directories.

- Each fixture should record the raw evidence window, normalized model output, rendered screenshot manifest, and the assertion that connects them.

Tier 3: release/native parity gate.

- Heavier Windows-native screenshot and manifest generation belongs in release or pre-release CI, not every fast local loop.
- It should compare browser review, localhost/OBS, and Windows native against the same scenario matrix where all three surfaces exist.
- It should preserve screenshot manifest parity as the cross-surface authority for geometry and semantics: if overlay Y has three content columns enabled, all applicable surfaces should agree on the enabled columns, body bounds, and expected width for that exact data/settings case.
- Full raw-capture replay can be optional or nightly, but failures from compact release-gate fixtures should block release.

The parseable tracker for this plan is `tools/validation/overlay-scenario-contract.json`. It should stay in sync with this document and carry overlay-specific scenario keys, current coverage state, expected surfaces, and known gaps.

### Scenario Contract Roadmap

Evolve `tools/validation/overlay-scenario-contract.json` in three steps.

1. Contract coverage tests.

- First, make the JSON enforce coverage, not behavior.
- Every production overlay in `BrowserOverlayCatalog` must have one matrix entry.
- Every native overlay must declare `windowsNative: supported`; Garage Cover must explicitly declare `not_applicable`.
- Any scenario marked `covered` must point to a real screenshot artifact, fixture, test file, or validator rule.
- Any scenario marked `partial` or `missing` must include `gaps` or `assertions`.
- No scenario can reference an unknown surface, tier, status, or overlay id.
- This turns the JSON into a living checklist without making the suite brittle.

2. Scenario-driven tests.

- Next, selected scenarios become executable.
- The runner should read scenario ids such as `standings-minimum-scale` and map them to fixture/settings input, expected model fields, expected screenshot paths, and expected manifest assertions.
- Screenshot generation and validation should share one scenario registry instead of hand-maintaining lists in multiple tools.
- Compact replay fixtures should be able to declare a scenario id, such as `relative-practice-timing-real-data`, run production model replay, and assert the expected display behavior.

3. Application behavior descriptors.

- Do not make the app consume the validation JSON directly.
- Instead, extract stable product rules into app-owned descriptors, then make the JSON and tests reference those descriptors.
- Good app-owned descriptor fields: `surfaceSupport`, `noDataPolicy`, `chromePolicy`, `sizingPolicy`, `scalePolicy`, `sessionPolicy`, `obsReadinessPolicy`, and required `evidenceFields`.
- Tests should assert that app descriptors match the scenario contract, screenshot/replay artifacts match app descriptors, and browser/localhost/native manifests agree with app descriptors.

The intended loop is:

```text
production descriptor -> model/render behavior -> screenshot/replay manifest -> scenario contract
```

The JSON answers "what must we prove?" The app descriptor answers "what should the product do?" The manifests answer "what did this surface actually do?"

Current implementation checkpoint:

- Step 1 is represented by `tests/tools/test_overlay_scenario_contract.py`, which validates scenario-contract shape, overlay/surface/tier/status coverage, and durable evidence references.
- Step 2 is represented by `tools/validation/overlay_scenario_registry.py` and `tests/tools/test_overlay_scenario_registry.py`, which resolve selected scenario ids to screenshot artifacts, compact fixtures, test files, and validator hooks without running every scenario as behavior yet.
- Step 3 is seeded by `src/TmrOverlay.Core/Overlays/OverlayBehaviorDescriptorCatalog.cs` and `tests/TmrOverlay.App.Tests/Overlays/OverlayBehaviorDescriptorContractTests.cs`, which keep app-owned behavior descriptors aligned with the scenario contract and production browser overlay catalog.
