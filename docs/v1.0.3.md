# v1.0.3 Planning

## Deferred From v1.0.2

V1.0.2 closed the local implementation and validation work that could be done from deterministic fixtures, uploaded CI logs, and the current captures. The items below should not remain open in the V1.0.2 tracker because the next useful step is fresh diagnostic capture, real Windows/OBS validation, or a product decision that is larger than the V1.0.2 hardening branch.

### Capture And Real-Validation Items

- V102-010: prove visual layout with live overlay screenshot capture and localhost route pixels enabled. A support bundle that only has semantic overlay state should continue to say it cannot prove pixels.
- V102-011: collect a deliberate pit/setup-change capture where the driver changes wing/ARB or another setup control, then decide whether any live telemetry, IBT field, or session-info diff can support user-facing Pit Service rows.
- V102-012 and V102-044: validate track-map provenance and live replacement in a real run. The capture should prove when a map is generated during finalization, recovered on startup, selected from storage, and reloaded by the running Track Map overlay instead of staying on the fallback circle.
- V102-022 and V102-046: reproduce settings/overlay interaction issues on Windows with diagnostics enabled. Capture overlay topmost/no-activate/input-transparent transitions, settings close/exit/update-state breadcrumbs, and pixel evidence for any flash or post-update close blockage.
- V102-032: keep transient update-check failures visible in diagnostics and validate a run where failed startup/manual checks are followed by a successful final state.
- V102-035 and V102-036: collect a race or team/focus-switch capture that proves local-player fuel/strategy evidence separately from focused/reference-car progress, then decide whether any product copy or post-race summary needs further refinement.
- V102-038: collect lap-delta examples with usable nonzero values before any overlay or analysis surface treats lap-delta fields as trustworthy.
- V102-040: run a real OBS-style long session after the new budget classifications. Use performance logs to scope any timer cadence, repeated settings-apply, Gap payload, localhost polling, or memory-retention optimization.
- V102-042 and V102-048: collect flag reproductions with raw `SessionFlags` and `CarIdxSessionFlags` evidence for ordinary yellow, debris, waving yellow, random waving, caution, waving caution, and one-to-green. Debris must remain orange/yellow striped instead of plain yellow, and caution/one-to-green should stay distinct because they imply safety-car/caution-period state.
- V102-047: collect Car Radar side-transition evidence while comparing against iRacing spotter calls. The first target is side-stability correctness; richer positional precision can remain a later product improvement.

## Overlay Visibility Modes

Add overlay visibility controls for driver state:

- in car
- out of car
- spotting
- garage

Evaluate whether these should replace or take priority over the current practice / qualifying / race visibility settings. The goal is to let users express when an overlay is useful by real usage context instead of only by session type.

Open decisions:

- Whether session-type visibility should remain as an advanced filter, become a secondary condition, or be retired.
- Which telemetry signals reliably distinguish in-car, out-of-car, spotting/spectating, and garage/setup states.
- How each overlay should default across those states, especially Pit Service, Inputs, Track Map, Car Radar, Garage Cover, and Stream Chat.
