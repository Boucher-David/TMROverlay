# V1.1 Overlay Data And Replay Forensics Tool Proposal

## Problem Statement

The 2026-05-22 Dallara P217 LMP2 / Gesamtstrecke Long captures proved that the current evidence model is good at preserving raw telemetry and post-session summaries, but weak at answering the product question that matters after a live race:

> At this exact moment, what did each overlay see, what should it have shown, and what did each surface actually render?

Raw `capture-*` folders preserve the telemetry truth. Diagnostics bundles preserve route counters, final model snapshots, rolling performance, and optional screenshots. The missing layer is an aligned replay artifact that joins raw frames, normalized live state, per-overlay model payloads, renderer output, screenshots, semantic manifests, OBS activity, Windows-native state, and performance samples on the same timeline.

The two full-race bundles showed why this needs to be a first-class V1.1 tool:

- final diagnostics snapshots are often disconnected/stale because bundle creation happens during session finalization
- localhost/OBS request counters can prove a source polled, but not what rows or labels were rendered
- screenshots were disabled, so there is no pixel evidence for visible overlays
- existing analysis scripts can decode captures, but they are ad hoc and overlay-specific
- user-observed issues such as lightly flashing Standings, Radar timing on a multiclass car behind the player, and Garage Cover not appearing in OBS require frame/event evidence, not just aggregate counts
- the race-long meatball flag in these full races was real, so the tool must prove local-driver flag context rather than assuming a long-lived meatball is false

The V1.1 goal is a repeatable forensic pipeline that turns a raw capture plus optional diagnostics bundle into a durable overlay evidence package.

## Collection Boundary

The V1.1 tool must not turn ordinary diagnostics into high-fidelity collection.

On Windows, high-fidelity replay evidence is allowed only after the user intentionally enables **Enhanced iRacing Telemetry Capture** in Support before the session. The existing developer/config override path (`TelemetryCapture:RawCaptureEnabled=true` or an equivalent environment override) should remain a test-build escape hatch, but diagnostics must report that source explicitly; it should not look like silent default collection.

When enhanced capture is off:

- no raw `telemetry.bin` capture should be started
- no V1.1 per-frame model replay sidecars should be produced by the app
- no live pixel/screenshot capture should be promoted as V1.1 evidence
- compact default diagnostics may still record bounded counters, route activity, performance summaries, and final/last-active snapshots

The offline CLI may analyze a `capture-*` directory that the user or tester has already supplied. That is post-processing of an explicit capture, not a new Windows collection path.

Storage ownership:

- Live-session raw telemetry and enhanced V1.1 sidecars should be stored beside the session under `%LOCALAPPDATA%\TmrOverlay\captures\capture-*`.
- Diagnostics bundles under `%LOCALAPPDATA%\TmrOverlay\diagnostics` should package compact summaries, manifests, evidence-quality warnings, and references to the latest capture. They should not be the primary storage location for raw telemetry or bulky replay/pixel artifacts.
- App-owned forensics packages should go under `%LOCALAPPDATA%\TmrOverlay\forensics\<capture-id>`. When enhanced capture finalizes, the app creates the starter package there automatically; the offline tool can enrich that package from the explicit `capture-*` input. In a development checkout, `--output artifacts/overlay-forensics/<capture-id>` remains useful for disposable experiments.

## Implementation Status

Initial scaffold exists at `tools/analysis/overlay_forensics.py`.

Implemented now:

- raw capture frame-header scan for `telemetry.bin`
- input inventory for capture and diagnostics sidecars
- live-overlay diagnostics event ingestion
- localhost/OBS route and page-event coverage checks
- performance JSONL timeline summaries
- per-overlay semantic result files
- sample-plan generation around baseline frames and diagnostics events
- production model replay orchestration through `tools/TmrOverlay.OverlayModelReplay`
- browser/localhost renderer replay screenshot hook through `tools/browser-review/render-model-replay-screenshots.mjs`
- explicit evidence-gap reporting for missing pixels, final disconnected snapshots, skipped model replay, skipped renderer replay, and native Windows validation

Not implemented yet:

- row/text-level semantic manifests
- Windows-native replay execution

Current execution caveat: the production model replay tool is a Windows-targeted .NET tool because it reuses the app assembly and production overlay model factory. On machines without `dotnet`, `overlay_forensics.py` records the exact replay command and marks model/renderer replay as skipped instead of substituting Python approximations.

## Requirements

Functional requirements:

- Accept one raw `capture-*` directory and an optional matching diagnostics bundle.
- Require an explicit raw capture input. If a diagnostics bundle has no matching raw capture, report a semantic-only evidence gap instead of inventing replay data.
- Decode `capture-manifest.json`, `telemetry-schema.json`, `telemetry.bin`, `latest-session.yaml`, and `session-info/*` according to `docs/capture-format.md`.
- Ingest `live-overlay-diagnostics.json`, `metadata/localhost-overlays.json`, `metadata/localhost-overlay-models.json`, `metadata/performance.json`, `performance/*.jsonl`, `metadata/evidence-quality.json`, `metadata/live-telemetry-synthesis.json`, and overlay-specific metadata when present.
- Select frames and events that explain overlay behavior, not just evenly spaced frames.
- Rebuild or capture per-overlay model payloads for the selected frames.
- Render browser-review and localhost/OBS screenshots from the exact sampled payloads where a browser renderer exists.
- Produce semantic manifests that can be validated without human pixel guessing.
- Compare "raw telemetry expected state" against "overlay model saw" and "renderer showed".
- Report OBS readiness failures when an overlay has live data but no corresponding localhost route/model requests.
- Separate live-session performance from finalization/bundle performance.
- Preserve explicit evidence gaps, especially missing Windows-native execution or missing pixel evidence.

Non-functional requirements:

- Keep high-fidelity collection opt-in through the Support enhanced-capture toggle on Windows; do not enable it from ordinary diagnostics bundle creation.
- Do not mutate raw captures or diagnostics bundles.
- Do not overwrite an enriched app-owned forensics package with a starter package during finalization or startup recovery.
- Keep output compact enough to commit selectively or attach to issues.
- Reuse existing analysis helpers before adding duplicate binary/YAML parsing.
- Prefer production/shared overlay model contracts over Python reimplementations of display logic.
- Keep privacy boundaries explicit: do not copy full raw telemetry, full session YAML, private chat tokens, or unnecessary driver identity fields into shareable artifacts.
- Keep older captures readable; missing sidecars should degrade to warnings, not failures.

Useful options:

- `--capture`: required raw capture directory
- `--diagnostics`: optional diagnostics bundle directory
- `--output`: optional output directory; when omitted on Windows, defaults to `%LOCALAPPDATA%\TmrOverlay\forensics\<capture-id>` and may enrich the app-created starter package
- `--overlays`: comma-separated overlay ids, default all known overlays
- `--strategy`: `default`, `dense`, `transitions-only`, `steady-state`, `issue-repro`
- `--events`: comma-separated event selectors
- `--frames`: explicit 1-based frame indexes or ranges
- `--time`: session-time or UTC-time ranges
- `--cadence`: baseline sampling cadence, for example `1hz`, `2hz`, `30s`
- `--window-before` / `--window-after`: context around selected event frames
- `--render`: `none`, `browser`, `localhost`, `native`, or a comma-separated set
- `--model-replay`: `auto`, `off`, or `required`; `auto` records a skipped gap when .NET is unavailable
- `--model-replay-command`: explicit production model replay command template
- `--renderer-command`: explicit browser/localhost replay renderer command template
- `--assert`: `warn`, `strict`, or `off`
- `--redaction`: `local`, `shareable`, or `full`
- `--fail-on`: `none`, `semantic`, `render`, `missing-evidence`

## Data Flow

1. Inventory inputs.

   Read capture manifest/schema, session YAML snapshots, diagnostics metadata, performance JSONL, localhost route counters, and evidence-quality warnings. Emit an input inventory before any expensive scan.

2. Build a capture index.

   Use the existing binary readers from `tools/analysis/extract_live_telemetry_fixture_corpus.py`, `tools/analysis/analyze_capture_assumptions.py`, and `tools/analysis/export_standings_browser_replay.py` as the starting point. Index frame headers, session-info update ranges, key scalar fields, and selected car-index arrays.

3. Detect event candidates.

   Generate a timeline of important transitions: session state, scoring source, row count, class headers, focus car, nearby cars, `CarLeftRight`, multiclass approaches, pit-service commands, fuel level increases, flags, track-map source, weather state, garage visibility, stale/disconnect boundaries, and overlay availability changes.

4. Select replay frames.

   Combine event windows with sparse baseline samples. Deduplicate frames across overlays while preserving overlay-specific reasons for selection.

5. Rebuild live snapshot and overlay model payloads.

   Short term, Python can produce compact expected-state payloads for raw telemetry and can continue using the existing Standings replay exporter. Durable V1.1 should add a replay host that calls the same normalized live-state and overlay model contracts used by the Windows app and localhost model factory. The report must label any Python-derived expected model as an approximation.

6. Render selected payloads.

   Browser review and localhost screenshots should be generated from the sampled payloads, not from the final disconnected app state. Windows-native screenshots should be generated on Windows by replaying the same selected frames through native render paths.

7. Validate semantics.

   Run overlay-specific checks against the raw expected state, model payload, render manifest, route counters, and screenshots.

8. Write artifacts.

   Emit JSON, Markdown, screenshots, manifests, and a compact issue-oriented summary.

## Frame And Event Sampling Strategy

Default strategy:

- Always sample session start, green/start, each lap transition, final lap/checkered, and disconnect/stale boundary.
- Add a sparse baseline every 30 seconds.
- Add event windows around overlay-specific transitions.
- Use denser sampling inside event windows, for example 2 Hz or exact transition frame plus +/- 1, 5, and 10 seconds.
- Cap output per overlay, but never drop the first and last example for each event kind.

Core event selectors:

- `session-state-transition`: `SessionState`, `SessionNum`, session kind, green/checkered
- `scoring-source-transition`: StartingGrid to SessionResults, row source changes, row count changes
- `class-header-change`: class group count/order/name changes
- `reference-row-change`: player/focus row position/class-position/lap/gap changes
- `car-left-right-transition`: raw `CarLeftRight` clear/left/right changes
- `radar.multiclass-approach`: nearby faster/slower class behind/ahead and closing timing
- `fuel-level-increase`: refuel windows and net fuel gain
- `measured-burn-readiness`: completed green lap and measured burn availability changes
- `pit-service-change`: `PitSvFlags`, `PitSvFuel`, tire/repair commands, pitstop active state
- `flag-transition`: raw `SessionFlags`, `CarIdxSessionFlags`, display model label/tone changes
- `track-map-source-change`: generated map vs fallback, marker/racing-line availability
- `weather-change`: wetness, declared wet, precipitation, temperatures, wind
- `garage-visibility-change`: `IsGarageVisible`, stale/disconnect, image availability
- `availability-change`: overlay should-render/hidden/status changes
- `performance-spike`: paint/update p95 or individual over-budget samples when timestamp-aligned evidence exists

Issue-specific presets:

- `standings-flash`: scoring source, row count, class header, reference row, availability, and render cadence changes
- `radar-multiclass-behind`: multiclass approach, side signal, timing/spatial placement, fade/hide windows
- `garage-cover-obs`: garage visibility, disconnect/stale, product enabled state, image readiness, OBS route polling
- `fuel-pit-service`: pit-service command changes, pit windows, refuel deltas, measured burn readiness
- `flags-local-context`: global flags, car-index flags, local repair/meatball/black/white/checkered display context

## Per-Overlay Semantic Checks

### Standings

- Raw scoring data exists when the overlay reports unavailable.
- StartingGrid and SessionResults transitions do not cause empty rows unless no scoring data exists.
- Class headers are present and ordered when rows from multiple classes are displayed.
- Reference row is stable across adjacent frames unless focus/player car changes.
- Overall position, class position, car number, driver label, lap, gap, interval, pit state, fastest lap, and last lap match the source row.
- Row count changes are explainable by session phase, source transition, or configured row budget.
- Repeated should-render true/false transitions inside a stable race window are flagged as likely flashing.
- OBS readiness fails if raw scoring exists and the expected OBS scene never requests `standings`.

### Relative

- Nearby row ordering matches distance/time relative to the focus car.
- Same-lap, ahead, behind, lap-ahead, lap-behind, and pending relationship states are explicit.
- Rows are not hidden solely because relationship inference is pending when timing/spatial data is otherwise usable.
- Class/color labels are stable across adjacent frames.
- Gaps near lap wrap are marked pending or lap-equivalent instead of showing misleading seconds.

### Gap To Leader

- Data appears only in race sessions.
- Class leader and reference rows are present before a class gap is displayed.
- Gap text uses seconds/laps consistently and does not jump without a matching lap/progress discontinuity.
- Graph history is retained through live race samples and not judged from final disconnected snapshots.
- Native paint/update costs are flagged when over the 16.667 ms frame budget.

### Car Radar

- `CarLeftRight` left/right maps to the displayed side.
- The visible hold/fade duration after a side signal follows the product contract.
- Timing-only and spatial-placement candidates are labeled in the evidence.
- Multiclass approach behind the player is detected from class, relative position, estimated time, lap distance, and closing context even when raw side signal is sparse.
- A side signal without a placement candidate still produces the intended generic side warning.
- Radar is hidden in garage/pit/unavailable contexts and visible during valid on-track risk windows.

### Fuel Calculator

- Fuel level and fuel percentage match raw fields after unit conversion.
- Instantaneous burn and measured burn sources are labeled separately.
- Measured burn becomes available when completed green lap evidence is sufficient.
- History/model fallback is labeled as fallback, not current-session measured burn.
- Pit/refuel windows detect net fuel increases when fuel rises during or near pit service.
- Additional fuel target and laps remaining are stable unless fuel, lap, stint, or race projection inputs changed.

### Pit Service

- `PitSvFlags`, fuel request, tire request, repair request, fast repair, and pitstop active state are decoded consistently.
- Requested service is shown only when the command is active and context allows it.
- Service completion/refuel evidence matches fuel deltas and pit-window timing.
- OBS readiness fails if pit-service signals exist and the expected OBS scene never requests `pit-service`.

### Flags

- Raw global `SessionFlags` and car-index/local flag sources are recorded separately.
- Local-driver critical flags, including meatball, black, repair, and disqualification states, require local-driver evidence or a documented source mapping.
- The 2026-05-22 full races must be treated as real race-long meatball cases when used as fixtures; long duration alone is not a failure.
- White and checkered displays require session phase/lap evidence and should not persist into stale disconnected snapshots as live state.
- OBS readiness fails if flag evidence exists and the expected OBS scene never requests `flags`.

### Track Map

- Sector count, marker count, highlighted sectors, live timing state, and selected map source are preserved.
- Generated map vs circle fallback is explicit in the model and screenshot manifest.
- First-race fallback behavior and second-race generated-map reuse can be proven from retained payloads.
- Highlight status, personal-best, best-lap, and full-lap highlight states match live timing evidence.
- Map bounds and geometry contract hashes are recorded for drift checks.

### Input State

- Throttle, brake, steering, clutch, gear, RPM, speed, and ABS state match raw fields and unit/scale conversions.
- Clutch engagement is converted to driver-control scale consistently.
- Gear shifts and pedal/steering transitions are sampled.
- Unavailable/no-content states do not render a misleading placeholder when product behavior is no-render.

### Session Weather

- Air/track temperature, wetness, declared wet, precipitation, skies, humidity, fog, wind speed, and wind direction match raw fields and units.
- Wet/dry labels distinguish track wetness from declared wet and precipitation.
- Visibility follows session/content gating and does not depend on final disconnected state.

### Garage Cover

- Route readiness, image readiness, product enabled state, garage visibility, stale telemetry, and disconnect are reported separately.
- OBS behavior is checked against intended policy: route polling, product enabled state, fresh telemetry, and `IsGarageVisible=true` are all required before the cover should render.
- Missing image, ready image, garage visible, garage hidden, stale telemetry, and disconnected telemetry are separate fixture states.

### Stream Chat

- Provider connection state, route state, retained message count, and rendered row count are reported.
- Chat evidence is not replayed from raw iRacing telemetry; it is diagnostics/provider evidence only.
- Private widget URLs and tokens are redacted.

## Browser Review, Localhost, And Windows-Native Integration

Browser review:

- Use browser review as the local deterministic renderer for sampled payloads.
- Render screenshots with Playwright from static replay JSON or a local replay endpoint.
- Capture DOM-derived semantic manifests alongside pixels: visible text, row count, data attributes, bounds, and model hash.

Localhost/OBS:

- Reuse the same overlay route ids and model API ids that OBS uses.
- Report route coverage from diagnostics: html requests, model requests, render events, hidden events, model errors, and recent page events.
- For replay, serve sampled payloads through a replay localhost mode so screenshots represent the payload under review, not the current live app state.
- Treat "raw data exists but OBS never requested the route" as a readiness failure when the overlay is expected in the scene.

Windows native:

- On non-Windows machines, trace native model/render source paths and record `nativeEvidence.status=not-run`.
- On Windows, replay selected frames through the native overlay renderers and capture form-render or desktop-crop screenshots.
- Record native form bounds, opacity, visibility, topmost/no-activate/click-through state, renderer id, geometry contract hash, and screenshot hash.
- Compare native semantic manifests against browser and localhost manifests for drift.

Shared contracts:

- Any geometry, row budget, column width, crop bound, hit area, or screenshot-semantic field used by validators must come from a shared contract.
- Output should include contract hashes from diagnostics where present, especially `overlay-geometry-contract.json` and shared browser/native contract files.

## Phased Implementation Plan

### Phase 0: Proposal And Fixture Selection

- Keep `v1.2.md` as the current evidence backlog; this proposal remains historical V1.1 tool-design context.
- Add this proposal as the tool design.
- Mark the two 2026-05-22 full-race pairs as initial fixtures.
- Add issue notes for Standings flashing, Radar multiclass-behind timing, Garage Cover OBS hidden behavior, Fuel measured burn/refuel detection, and OBS source coverage.

### Phase 1: Python Inventory, Index, And Report

- Create `tools/analysis/overlay_forensics.py`.
- Reuse capture decoding helpers from existing analysis tools.
- Ingest diagnostics bundle metadata and performance JSONL.
- Emit input inventory, event index, sample plan, and Markdown summary.
- Implement OBS readiness checks and evidence-gap reporting.
- No rendering required in this phase.

### Phase 2: Sampled Expected-State Payloads

- Add per-overlay expected-state JSONL for selected frames.
- Start with overlays already partially supported by existing tools: Standings, Relative/Gaps source fields, Fuel/Pit, Radar, Flags, Track Map, and Input.
- Label Python-derived model fields as expected telemetry state, not production model truth.
- Promote the ad hoc Standings replay exporter into the new sample/export pipeline.

### Phase 3: Production Model Replay Host

- Add a replay host that feeds selected raw frames into the same normalized live-state and overlay model builders used by production.
- Output exact overlay model payloads with model hashes.
- Keep the host headless and deterministic.
- Prefer shared Core/App model services over duplicating display logic in Python.

### Phase 4: Browser And Localhost Rendering

- Add a replay data server or static fixture route for browser review.
- Render sampled payloads through Playwright.
- Produce screenshots and DOM semantic manifests.
- Add route/model parity checks between browser review and localhost/OBS payloads.

### Phase 5: Windows-Native Evidence

- Add Windows-only native replay execution.
- Capture native screenshots and semantic manifests.
- Compare native/browser/localhost row counts, text, availability state, and geometry contract hashes.
- Keep non-Windows runs explicit about the validation gap.

### Phase 6: CI And Branch-Complete Integration

- Add a small deterministic fixture set to local tests and CI. These fixtures should be compact JSON/frame summaries derived from real captures, not committed `telemetry.bin`, diagnostics zips, or large capture folders.
- Run production model policy checks against those compact fixtures in normal C# test jobs so regressions fail before screenshot or full forensics stages.
- Add strict semantic checks for known V1.1 regressions once fixed.
- Keep large real captures local/manual by default, with compact derived artifacts committed only when appropriate.
- Hook the report into screenshot validation and diagnostics bundle review workflows.

Proposed CI shape:

- Tier 1: C# production-model golden tests. Feed compact real-capture-derived frame summaries into the same live-state/model builders used by the app and assert overlay policy decisions such as render/hidden, row counts, source labels, and evidence reasons. These run in the normal local and CI test jobs.
- Tier 2: browser and localhost contract tests. Initial wiring is `tests/browser-overlays/forensicsFixtureContracts.test.js` in `npm run test:settings-effects`; it renders the compact Garage Cover fixture through browser-review model contracts and the localhost browser-source shell, then compares route ids, rendered/hidden decisions, visible image source, browser-source events, shared settings hashes, and shared geometry.
- Tier 3: forensics tool smoke and golden tests. Initial wiring is `tests/tools/test_overlay_forensics.py` in the Windows static Python unittest lane; it runs `overlay_forensics.py` against tiny fixture packages under `fixtures/telemetry-analysis/forensics-smoke/` and validates OBS/readiness classification without committing full capture folders.
- Tier 4: optional full-capture replay. Run large race captures from local storage or CI artifacts on demand or nightly, never as required committed repo data. Failures here should file evidence-backed follow-up issues unless the branch explicitly changes replay semantics.

The default CI failure should identify the layer that regressed: raw/frame extraction, production model policy, localhost/OBS route readiness, browser/native rendering, diagnostics evidence, or screenshot geometry.

## Validation Plan

Tool unit tests:

- Binary frame header parsing and random-access frame reads.
- Session-info snapshot lookup by `sessionInfoUpdate`.
- Field availability and missing-field behavior.
- Event selector detection for synthetic mini captures.
- Redaction modes.
- Diagnostics ingestion with missing optional files.

Golden fixture tests:

- Use compact fixtures derived from the two 2026-05-22 full-race captures plus the 2026-05-23 Navarra OBS/Garage Cover test. Each fixture should preserve only the frame/model fields required for the target assertion.
- Assert OBS readiness failures for overlays that had raw data but no OBS requests in those bundles.
- Assert Garage Cover's product policy through the production model: route/image readiness alone does not render; disabled never renders; enabled + fresh `IsGarageVisible=true` renders; enabled + garage hidden, stale telemetry, disconnected telemetry, or settings preview stays hidden.
- Assert Fuel measured-burn readiness and pit fuel-increase checks catch the known race-2/race-1 evidence gaps after semantics are finalized.
- Assert the race-long meatball fixture is classified as local-driver-supported or manually annotated real, not automatically false.
- Assert Standings flashing checks detect repeated render/availability or row/source instability in a controlled fixture.
- Assert Radar multiclass-behind checks select the relevant event windows.

Renderer tests:

- Browser screenshots exist for each sampled visible state.
- No-data/unavailable samples prove hidden/no-render behavior where expected.
- Screenshot manifests include model hash, visible text, row count, bounds, renderer id, and image hash.
- Browser and localhost render the same semantic payload for the same sample.
- Windows-native tests run only on Windows and report skipped/not-run elsewhere.

Performance validation:

- `performance-timeline.json` separates live overlay paint/update metrics from finalization/bundle metrics.
- Over-budget live paint samples are tied to timestamp windows when possible.
- Capture health includes frames written, pending messages, dropped frames, and telemetry FPS.

Manual acceptance for V1.1:

- Given a raw capture and diagnostics bundle, the report can answer for every overlay:
  - whether telemetry existed
  - whether the model should have had content
  - whether OBS requested it
  - what sampled payload was generated
  - what each renderer showed
  - which semantic checks passed or failed
  - what evidence is still missing
- The tool can produce a focused repro package for Standings flashing and Radar multiclass-behind timing without rereading every artifact by hand.
- The tool makes final disconnected diagnostics snapshots useful context, but never mistakes them for live race render proof.
